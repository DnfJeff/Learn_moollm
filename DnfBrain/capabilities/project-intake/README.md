# project-intake — why the flow exists

**This is the project-intake capability's backstory: why "I've got a new project" gets a
procedure instead of an ad-hoc folder, and where changes are noted.**

## The idea

Every knowledge system dies the same death: work happens *next to* it instead of *through*
it, and the findings evaporate with the chat that produced them. The intake flow makes the
library the path of least resistance at the exact moment a project begins — three questions,
one template copy, and the instance is standing, wired by `references/` to the shelves it
will draw on and feed. The end of the project is decided at the start: promotion becomes a
walk down a list.

## Why it's also a test bench

This flow is deliberately procedure-shaped — announce, interview, instantiate, wire,
register, validate — so it can be run as a benchmark against different host models (the
patterns are proven on flagship models; the interesting question is what a small local model
can execute faithfully). A run is judged on: did the instance land in the right place, is
`references/` wired, is the by-project row present, does `validate.py` pass. All checkable
from the files, which is the point.
